# 1. PART I — GIT & GITHUB COLLABORATION (40 MARKS)

## The master mental model

```text
REMOTE REPOSITORY (GitHub)
        ↑ push
        |
LOCAL BRANCH / HISTORY
        |
        +---- commit <---- add <---- working files
        |
        +---- merge / rebase
        |
        +---- stash <---- temporary uncommitted work
```

The commands in the paper are easiest to remember by direction:

```text
clone   = GitHub → local repository
fetch   = remote updates → local remote-tracking refs
pull    = fetch + integrate into current branch
push    = local branch → GitHub
add     = working tree → staging area
commit  = staging area → history
revert  = create new commit that undoes an old commit
reset   = move HEAD/branch pointer
rebase  = replay commits on a new base
stash   = temporarily store uncommitted work
merge   = combine branch histories
```

## Q3. Inspect staged, unstaged, and untracked changes

SET-6 scenario mentions `index.jsp` modified and `schedule.jsp` created.

SET-7 scenario mentions `index.jsp` modified and `complaints.jsp` created.

### Command

```bash
git status
```

### What it tells you

`git status` reports the state of the working tree and index, including:

```text
Changes to be committed     → staged
Changes not staged           → modified but unstaged
Untracked files              → new files not tracked by Git
```

### Expected output example

```text
On branch feature/player-registration

Changes not staged for commit:
  modified:   src/main/webapp/index.jsp

Untracked files:
  src/main/webapp/schedule.jsp
```

The exact status depends on what was staged before the command.

### Remember

> **"What has changed?" → `git status`**

`git diff` is for actual line-level content differences; `git status` is for change state/categories.

## Q10. Rebase the local feature branch onto updated `main`

First ensure you are on the feature branch and `main` contains the desired base.

```bash
git rebase main
```

### Short explanation

Git takes the feature branch's commits and replays them on top of the tip of `main`.

### Before

```text
A---B---C      main
     \
      D---E    feature
```

### After rebase

```text
A---B---C---D'---E'   feature
```

### Expected output

```text
Successfully rebased and updated refs/heads/feature/player-registration.
```

### Remember

> **Rebase = move/replay your feature commits onto a new base.**

`merge` combines histories; `rebase` rewrites the base/history.

---

## Q11. Cancel a failed rebase

```bash
git rebase --abort
```

### Short explanation

Abandons the in-progress rebase and returns the repository to its pre-rebase state as far as Git can restore it.

### Remember

During rebase conflicts:

```bash
git rebase --continue   # after resolving conflicts

git rebase --abort      # give up and return to pre-rebase state
```

## Q12. Safely undo a bad commit while preserving history

First discover the hash if the question does not provide it:

```bash
git log --oneline
```

Then:

```bash
git revert <commit-hash>
```

Example:

```bash
git revert a7c91de
```

### Short explanation

`git revert` creates a **new commit** that reverses the selected commit. The original bad commit remains in history.

### Before

```text
A---B---C   ← bad commit
```

### After

```text
A---B---C---R
           ↑
       revert commit
```

### Expected output

```text
[feature/... xyz7890] Revert "..."
```

### Remember

> **Undo changes + preserve commit history = `git revert`**

Do not use `reset` when the wording explicitly says to preserve history.

## Q13. Undo the last commit but keep all its changes staged

```bash
git reset --soft HEAD~1
```

### Short explanation

Moves `HEAD` back one commit, while leaving the working tree and index unchanged. Therefore the changes from the undone commit remain staged.

### Before

```text
A---B---C  ← HEAD
```

### After

```text
A---B  ← HEAD
```

The content that was committed in `C` is still staged.

### Verify

```bash
git status
```

It should report the changes under:

```text
Changes to be committed:
```

### Critical reset table

| Command | HEAD moves back? | Working files kept? | Changes staged? |
|---|---:|---:|---:|
| `git reset --soft HEAD~1` | Yes | Yes | **Yes** |
| `git reset --mixed HEAD~1` | Yes | Yes | No |
| `git reset --hard HEAD~1` | Yes | No | No |

### Remember

> **Keep changes staged = `--soft`**

## Q14. Stop tracking `db-config.env` but keep the local file

Both SET-6 and SET-7 use the same path:

```bash
git rm --cached src/main/resources/db-config.env
```

### Short explanation

Removes the file from Git's index/tracking area while keeping the file in the working directory.

### Expected output

```text
rm 'src/main/resources/db-config.env'
```

### Compare carefully

```bash
git rm <file>
```

removes the file from Git **and** the working tree.

```bash
git rm --cached <file>
```

removes it from Git tracking but **keeps the local file**.

### Remember

> **Keep local file = `--cached`**

For a real credentials/config file, also add it to `.gitignore` after untracking it. That is practical hygiene; the paper only asks for the untracking operation.

## Q20. Push `main` and prove local/remote point to the same commit

```bash
git push origin main
git fetch origin
git rev-parse main
git rev-parse origin/main
```

### Why fetch after push?

It refreshes your local `origin/main` reference so the comparison is based on current remote-tracking data.

### Expected result

```text
def5678abcdef...
def5678abcdef...
```

The two hashes should be identical.

### Why this proves equality

A Git branch/ref ultimately points to a commit object. If:

```text
main
```

and:

```text
origin/main
```

resolve to the exact same commit hash, both are at the same commit point.

### Remember

> **Push → fetch → compare hashes**

# Q1. POM Validation & Plugin Debugging [6M]

## Q1(a). `mvn validate` and XML schema/POM errors

### Command used to expose the issue

```bash
mvn validate
```

### What to inspect

Look for malformed XML such as:

```xml
<scope>provided
```

when it should be:

```xml
<scope>provided</scope>
```

### Why Maven rejects malformed XML

Maven must parse the POM before it can construct a valid project model. If XML tags are not properly nested/closed, Maven cannot parse the model and fails before normal build phases proceed.

### SET-7 supplied POM exact correction

The POM you supplied in the preceding discussion contains:

```xml
<dependency>
    <groupId>javax.servlet</groupId>
    <artifactId>javax.servlet-api</artifactId>
    <version>4.0.1</version>
    <scope>provided
</dependency>
```

Correct it to:

```xml
<dependency>
    <groupId>javax.servlet</groupId>
    <artifactId>javax.servlet-api</artifactId>
    <version>4.0.1</version>
    <scope>provided</scope>
</dependency>
```

### Expected error idea

The exact parser wording depends on Maven/XML parser version, but it will indicate a malformed/non-parseable POM or a missing closing tag.

### Exam answer pattern

> The `<scope>` element is not properly closed. XML requires a matching closing `</scope>` tag. Maven therefore cannot parse the POM/project model and fails during model construction.

# Q2. Dependency Resolution & Lifecycle Failures [6M]

## Q2(a). MySQL connector dependency

The correct modern MySQL Connector/J coordinates are:

```xml
<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
    <version>8.0.33</version>
</dependency>
```

### SET-7 supplied POM defect

It contains:

```xml
<groupId>com.mysql</groupId>
<artifactId>mysql-connector-invalid-artifact</artifactId>
<version>99.99.99</version>
```

The artifact ID is intentionally invalid, and `99.99.99` is not a normal published Connector/J release.

### Expected failure idea

```text
Could not find artifact
com.mysql:mysql-connector-invalid-artifact:jar:99.99.99
```

### Exam explanation

> Maven resolves a dependency using its artifact coordinates. The declared MySQL artifact ID/version do not correspond to an available Connector/J artifact, so dependency resolution fails. Use `com.mysql:mysql-connector-j` with a valid version.

### Important

The exact version required in a particular lab may be specified by the supplied POM/key. If so, use that exact valid version rather than blindly changing it.

## Q2(b). Test dependency scope

### Intended correction in the paper

```xml
<dependency>
    <groupId>junit</groupId>
    <artifactId>junit</artifactId>
    <version>4.13.2</version>
    <scope>test</scope>
</dependency>
```

JUnit is required for compiling/running tests but is not an application runtime dependency.

```text
Servlet API       → provided
Normal application library → compile/default
```

Normally Maven derives `finalName` from:


which would normally suggest:

BUT the POM explicitly overrides it with:

```xml
<finalName>ApartmentMaintenanceSystem</finalName>
```

Therefore the final WAR is:

```text
ApartmentMaintenanceSystem.war
```

### General rule

```text
<finalName> exists → use it
no <finalName> → normally artifactId-version
```

```bash

```

# Q4. Maven Core Concepts [5M]

## Q4(a). `<pluginManagement>` vs `<plugins>`

### `pluginManagement`

Used to define plugin configuration/defaults, especially for inheritance/reuse. By itself it does not make the plugin an active project plugin declaration.

Example:

```xml
<pluginManagement>
    <plugins>
        <plugin>
            <groupId>...</groupId>
            <artifactId>...</artifactId>
            <version>...</version>
        </plugin>
    </plugins>
</pluginManagement>
```

Think:

```text
pluginManagement = HOW the plugin is configured
```

### `plugins`

Declares the plugin for the project build.

```xml
<plugins>
    <plugin>
        <groupId>...</groupId>
        <artifactId>...</artifactId>
        <version>...</version>
    </plugin>
</plugins>
```

Think:

```text
plugins = USE this plugin in this project
```

### Exam comparison

| `pluginManagement` | `plugins` |
|---|---|
| Defines management/default configuration | Declares plugin for project use |
| Common in parent POMs/inheritance | Used directly in project build configuration |

## Q8(b). Why `javax.servlet-api` is `provided`

Correct dependency pattern:

```xml
<dependency>
    <groupId>javax.servlet</groupId>
    <artifactId>javax.servlet-api</artifactId>
    <version>4.0.1</version>
    <scope>provided</scope>
</dependency>
```

### Why?

The application needs the Servlet API at compile/test time, but a servlet container such as Tomcat supplies the Servlet API at runtime.

Conceptually:

```text
compile
Application + Servlet API
        ↓
      compile

runtime
WAR + Tomcat
        ↓
Tomcat supplies Servlet API
```

### If `provided` is omitted

Dependency scope defaults to `compile`. The Servlet API may then be treated as an ordinary application dependency and can be packaged in the deployment, creating duplicate/conflicting Servlet API classes relative to those supplied by Tomcat.

### Better exam wording

> `provided` means the application needs the dependency during compilation/testing but expects the runtime container to supply it. For a WAR deployed on Tomcat, Tomcat already provides the Servlet API. Omitting `provided` can cause the Servlet API to be included as an application dependency and lead to classloading/API-version conflicts.

### Remember

```text
Servlet API → provided
JUnit       → test
```
